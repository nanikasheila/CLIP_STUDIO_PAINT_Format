# V3 描画とプレビューの比較

ユーザーの PC にある実ファイル 719 件で、ライブラリの合成描画（`render.rs`）を CSP が保存したプレビュー（`CanvasPreview`）と比べた結果（R10）。
元ファイルは読み取りだけで、変更していない（制約 C2）。載せるのは件数と PSNR の集計だけで、画素・文字・レイヤー名・パスは含まない（N6）。

## 実施条件

| 項目 | 値 |
|---|---|
| 実施日 | 2026-10-25 |
| 対象 | V1 と同じ `.clip` 719 件 |
| 実行環境 | ユーザー PC 上の Linux VM（2 コア・メモリ約 3.9 GB）、`x86_64-unknown-linux-musl` の静的バイナリ、2 並列 |
| コマンド | `cspf corpus ROOT OUT.jsonl --render --shard K/2 --list LIST.txt`、集計は `tools/validation/v3_summary.py OUT.jsonl...` |
| 比べ方 | `render_like_preview`: プレビューの幅 ÷ キャンバスの幅の倍率で描き、プレビューと同じ大きさにする。両方を白の上に置いた RGB の PSNR（`render::psnr`、全画素一致は 99 dB と数える） |

## 受入の集合

R10 の受入は「ベクター・テキスト・3D・調整レイヤーを含まないファイル」の 90% 以上で 30 dB 以上。
`v3_summary.py` は描画の報告（`RenderReport`）から次のように分ける。

| 群 | 条件 |
|---|---|
| plain（受入の集合） | ベクターレイヤー・テキストレイヤー・色調補正レイヤー・3D がない |
| vector/text | ベクターかテキストのレイヤーがある |
| correction/3d | 上のどちらでもなく、色調補正レイヤーか 3D がある |

## 結果

**plain 279 件のうち 257 件（92.1%）が 30 dB 以上で、受入基準（90%）を満たす。** 描画のエラー 0 件、プレビューのないファイル 0 件。

| 群 | 件数 | 30 dB 以上 | p10 | 中央値 | p90 |
|---|---|---|---|---|---|
| plain | 279 | 257（92.1%） | 31.8 | 99.0 | 99.0 |
| correction/3d | 24 | 19（79.2%） | 19.0 | 39.8 | 50.1 |
| vector/text | 416 | 56（13.5%） | 10.0 | 18.4 | 32.4 |
| 全体 | 719 | 332（46.2%） | | | |

plain で 30 dB に届かない 22 件が持つもの（重複あり）: 作品情報のレイヤー（`story_info`、画素なし）10 件、画像素材 10 件、
レイヤー効果「ポスタリゼーション」2 件、画素のないベクターレイヤー 1 件、「水彩境界」1 件。
作品情報はプレビューに出ないので描かない（下の 3 章）。差が残る理由は、ほかの要素との重なりと画像素材の補間（2 章）と考えている。

### 機能ごとの集計（重複あり）

描画の報告から、各機能を「描いた」ファイルで分けた集計。1 つのファイルが複数の行に入る。
「機能をすべて実装したものだけ」の集合（ベクター・テキスト・トーン・画像素材・知覚的グラデーション・クリッピング・効果・色調補正のいずれも描かないファイル）は
110 件のうち 101 件（91.8%）が 30 dB 以上。

| 機能 | 件数 | 30 dB 以上 | 中央値 |
|---|---|---|---|
| 色調補正 | 85 | 33（38.8%） | 27.1 |
| クリッピング | 315 | 73（23.2%） | 16.4 |
| レイヤー効果 | 413 | 112（27.1%） | 19.0 |
| ベクター | 388 | 39（10.1%） | 17.7 |
| トーン（効果） | 87 | 2（2.3%） | 12.7 |
| 画像素材 | 120 | 26（21.7%） | 16.7 |
| テキスト | 301 | 27（9.0%） | 13.5 |
| 知覚的グラデーション | 46 | 0（0.0%） | 11.0 |

この表の値は、その機能そのものの誤差ではない（同じファイルのベクターやテキストの差が支配的なことが多い）。
合成モードごとの式と CSP の書き出しとの照合は [V6](V6-made-files.md) 3 章（28 モード、最大差 7/255）、
画素を持たないレイヤーは [V6b](V6b-generated-layers.md) にある。

ベクター・テキストが低いのは、CSP がそれらの画素を保存していないことが多く、ベクターはブラシの近似（[V6](V6-made-files.md) 7 章、05 章）、
テキストは CSP が描いた文字の画像（06 章）で描くため。これらは R10 の受入の対象外で、[未解明の一覧](../spec/README.md#未解明の項目) に残す。

## 2. 画像素材は原寸で描いてから縮める

画像素材レイヤー（`ResizableImageInfo`）は、変形した画像をプレビューの倍率で直接描くと、原寸で描いてから縮めたものより 3.7〜14 dB 低かった。
CSP は素材をキャンバスの大きさでレイヤーに描き、小さい表示は半分ずつ縮めて作る（ミップマップと同じ）と考えられる。
描画（`render.rs` の `material_at_canvas_size`）は次のとおり。

1. 配置の 4 つの角から、素材がキャンバスに占める範囲を求める（`Placement::bounds`）。始点は 256 px の格子にそろえ、キャンバスの内側に切る
2. 元の画像のミップマップから、倍率（1 以下に切る）以上の一番小さいレベルを選ぶ
3. その範囲だけを倍率 1 で描き（`draw_region`）、ほかのレイヤーと同じく原寸から縮める

範囲だけを描く方法は、キャンバス全体を描く方法と全件で同じ結果になり、メモリーの最大は 804 MB のファイルで約 3.4 GB に下がった。

## 3. 作品情報のレイヤー

作品情報（`story_info`）のレイヤーはプレビューに出ない（426 件にあり、描かないときに一致する）。描画では描かず、報告の `without_pixels` に数える。

## 4. 複数のまとまりを持つテキスト（2026-10-25、上の集計の後）

V7 で、文字のまとまりが複数あるテキストレイヤーの 1 つ目（`TextLayerString` / `TextLayerAttributes`）を読み落としていたことが分かり、直した（06 章）。
描画は CSP が描いた文字の画像を置くので、1 つ目のまとまりの文字が出ていなかった。
このテキストを持つ 245 件のうち 73 件を描き直して上の集計と比べた結果: 27 件が良くなり（最大 +10.2 dB）、7 件が下がり（最大 −2.2 dB）、
中央値は 18.4 → 18.5 dB、30 dB 以上の件数は変わらない（6 件）。下がった 7 件では、足したまとまりはどれも表示されていて、本文があり、CSP が描いた画像を持つ。
原因は確かめておらず、フキダシ付きの文字の置き場所（位置がフキダシの中心からの相対、06 章、未解明）を疑っている。上の表は直す前の値（R10 の受入の集合には影響しない）。

## 5. コマ枠フォルダーとフキダシ（2026-10-26、上の集計の後）

ベクターとテキストの差を減らすため、CSP が画素を保存していない 2 つを描くようにした。

- **コマ枠フォルダー**: 見えているコマ枠フォルダー 267 個（178 ファイル）のどれも、マスクと枠線（`ComicFrameLineMipmap`）の画素がない
  （`examples/frame_census.rs`）。マスクを持つのに画素がないほかのレイヤーはない。フォルダーのベクター（枠のオブジェクト）から、
  閉じた形を塗ってマスクにし（非ゼロの巻き数、4 × 4 の部分画素）、中身の上に枠線をフォルダーの不透明度で描く（03 章、05 章）
- **フキダシ**: テキストレイヤーのベクターがフキダシの形で、ヘッダー 96 の +72 が図形の種類（05 章）。13 ファイルにある。
  形を塗り（サブ色）、線（メイン色とブラシ）を描き、同じレイヤーのほかの形の塗りの中では線を消す（つながったフキダシが 1 つの輪郭になる）。
  しっぽは前のフキダシの色と線を使う。文字のまとまりはレコード 45 の番号のフキダシの中心からの相対に置く（06 章）

文字の位置は `examples/text_locate.rs` で確かめた: CSP が描いた文字の画像をプレビューの倍率に縮め、プレビューの暗さとの正規化相互相関が
最大になる位置を探す。2 ファイル 14 まとまりで、上の決まりの位置と ±2 px（プレビューの 1 px）で一致した。
フキダシの線と塗りの色の決まり（フラグ 0x2000 がなければ黒い線と白い塗り）は、そうしないとプレビューと合わない形から推測したもので、CSP で作った見本では確かめていない。

719 件を描き直し、上の集計（2 章・4 章で描き直したファイルはその値）と比べた結果:

| 群 | 件数 | 30 dB 以上 | 中央値 | 0.5 dB 以上良くなった | 0.5 dB 以上下がった |
|---|---|---|---|---|---|
| plain | 220 | 199 → 199 | 64.8 → 64.8 | 1 | 0 |
| correction/3d | 23 | 18 → 18 | 39.7 → 39.7 | 0 | 0 |
| vector/text | 475 | 115 → 115 | 21.0 → 22.8 | 187 | 0 |
| 全体 | 718 | 332 → 332 | 28.3 → 28.3 | 188 | 0 |

（この表の群は `tools/validation/v3_delta.py` の分け方で、描画の報告の数から分けるので上の表とは件数が違う。1 件は 170 秒を超えて打ち切った。）
良くなった 188 件の上がり幅は中央値 +7.3 dB、p90 +10.8 dB、最大 +19.6 dB（5 dB を超えたのが 140 件）。
`v3_summary.py` の機能ごとの中央値は、ベクター 17.7 → 21.2、テキスト 13.5 → 19.9、トーン 12.7 → 19.2、知覚的グラデーション 11.0 → 19.1 dB
（同じファイルのコマ枠が直ったため）。30 dB の線を越えたファイルはなく、多くは 20〜30 dB に上がった（25〜30 dB が 83 件）。
4 章で下がった 3 件は、フキダシの位置を直しても戻らなかった（原因は別）。

残る差として目で見えたもの: トーンとグラデーションの色、ラスターやベクターレイヤーに描かれたフキダシの線、
ベクターの塗りのリスト（`VectorNormalFillIndex`、今は線として描いている）、ベクターの線の太さと形の近似。

## 6. ベクターは原寸で描いてから縮める（2026-10-26、5 章の後）

5 章の後、ベクターかテキストを持つ 316 件（描画が 12 秒未満のもの）で、誤差をベクターの画素・テキストの画素・それ以外に分けた
（`examples/kind_ablation.rs`: ベクターレイヤー、テキストレイヤーをそれぞれ隠して描き直し、変わる画素の二乗誤差を数える）。
誤差の 38% がベクターの画素、12% がテキストの画素で、188 件ではベクターの画素の誤差がいちばん大きい。
ベクターの誤差がなかったとすると 30 dB 以上は 114 件から 160 件になる。CSP はこれらのベクターレイヤーの画素を保存していない。

プレビューは原寸の描画を 2 × 2 の平均で半分ずつ縮めたもの（画像素材と同じ、2 章）なのに、ベクターはプレビューの大きさで直接描いていた。
細い線は薄く、太い線は縁が硬くなる。ベクターレイヤー・コマ枠の線・フキダシを、オブジェクトを囲む 256 px 単位の範囲だけ原寸で描き、
ほかのレイヤーと同じ手順で縮めるようにした（`stroke::draw_layer_at_canvas_size`、`draw_balloons_at_canvas_size`）。
描画の時間はほぼ変わらない（描き直した 200 件の合計で 1,400 → 1,511 秒）。最大メモリーも変わらない（調べた 1 件で 1.08 GB）。

ベクター・テキスト・コマ枠のどれかを持つ 416 件を描き直し、5 章の結果と比べた結果:

| 群 | 件数 | 30 dB 以上 | 中央値 | 0.5 dB 以上良くなった | 0.5 dB 以上下がった |
|---|---|---|---|---|---|
| plain | 220 | 199 → 199 | 64.8 → 64.8 | 1 | 0 |
| correction/3d | 23 | 18 → 18 | 39.7 → 39.7 | 0 | 0 |
| vector/text | 475 | 115 → 145 | 22.8 → 25.8 | 309 | 10 |
| 全体 | 718 | 332 → 362（50.4%） | 28.3 → 30.1 | 310 | 10 |

良くなった 310 件の上がり幅は中央値 +2.7 dB、p90 +7.2 dB、最大 +15.3 dB。`v3_summary.py` の機能ごとでは、
ベクター 39 → 69 件（中央値 21.2 → 24.9 dB）、テキスト 27 → 35 件（19.9 → 23.7 dB）が 30 dB 以上になった。
下がった 10 件（最大 −2.8 dB）のうち見た 3 件は、CSP では紙の質感のある鉛筆のような線（画像や質感の先端、05 章で描かないもの）で、
原寸で描くと、もともと濃すぎた線がさらに濃くなる。

## 再現の手順

```sh
# PC 上で（ROOT は作品のフォルダー、LIST.txt は .clip のパスの一覧）
cspf corpus "$ROOT" out/v3_0.jsonl --render --shard 0/2 --list LIST.txt &
cspf corpus "$ROOT" out/v3_1.jsonl --render --shard 1/2 --list LIST.txt &
wait
python tools/validation/v3_summary.py out/v3_0.jsonl out/v3_1.jsonl
```

`corpus` は途中から再開できる（同じ出力に追記し、済んだファイルを飛ばす）。2 並列で大きなファイルが重なるとメモリー不足で止まることがあり、
そのときは止まった側だけを 1 つで実行し直す。
2 つの実行を比べるのは `python tools/validation/v3_delta.py OLD_0.jsonl,OLD_1.jsonl NEW_0.jsonl,NEW_1.jsonl`（一覧の後のファイルが前を上書きする）。
誤差の内訳は `cargo run --release -p csp-format --example kind_ablation -- "$ROOT" LIST.txt OUT.jsonl`、
コマ枠とマスクの数え上げは `cargo run --release -p csp-format --example frame_census -- "$ROOT" LIST.txt`。
